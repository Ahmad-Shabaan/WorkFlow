خلينا نشرح Outbox Pattern من الصفر، ونربطه بمشروع الـ WorkFlow والـ Hangfire اللي بتشتغل عليه.

## 1. إيه المشكلة اللي الـ Outbox Pattern بيحلّها؟

تخيّل إن عندك `Task` في مشروعك، والـ Manager غيّر حالتها إلى `Completed`. المطلوب إن النظام يبعت Notification للموظف.

العملية دي فيها حاجتين منفصلتين:

1. تحديث الـ Task في قاعدة البيانات.

2. إرسال الـ Notification عن طريق Email أو خدمة خارجية.

المشكلة إن العمليتين مش مضمون ينجحوا مع بعض.

### سيناريو من غير Outbox

1. Task Status = Completed

تم تحديث قاعدة البيانات بنجاح

2. إرسال Notification يفشل

مشكلة شبكة أو خدمة Email غير متاحة

النتيجة

الـ Task أصبحت Completed، لكن الـ Notification لم تصل، وممكن الحدث نفسه ما يتعالجش مرة تانية.

حتى لو استخدمت Hangfire، لازم تفكر في مشكلة مهمة: لو حدّثت الـ Task الأول، وبعدها التطبيق وقع قبل ما يسجل الـ Job في Hangfire، ممكن تفقد عملية الإرسال.

## 2. فكرة الـ Outbox Pattern

بدل ما تعتمد على عمليتين منفصلتين، بتسجل التغيير والحدث المطلوب معالجته في نفس Database Transaction.

بتضيف جدولًا مثل `OutboxMessages` يحتوي على الأحداث التي لم تتم معالجتها بعد.

### التدفق باستخدام Outbox

Database Transaction

تحديث Task إلى Completed

إضافة Outbox Message باسم TaskCompleted

Commit

التغيير والحدث يتحفظوا معًا أو لا يتحفظ أي منهما

Background Worker / Hangfire

يقرأ الأحداث غير المعالجة من جدول Outbox

Process Message

يبعت الـ Notification، ثم يحدّث حالة الرسالة

الفكرة الأساسية: لو التطبيق وقع بعد الـ Commit، الرسالة ما زالت محفوظة في قاعدة البيانات. لما الـ Background Worker يشتغل تاني، يقدر يلاقيها ويكمل المعالجة.

## 3. هتطبّقه إزاي في WorkFlow؟

ممكن تبدأ بجدول بسيط اسمه `OutboxMessages`:

| Column        | وظيفته                                |
| ------------- | ------------------------------------- |
| `Id`          | معرف الرسالة                          |
| `Type`        | نوع الحدث، مثل `TaskCompleted`        |
| `Payload`     | بيانات الحدث بصيغة JSON               |
| `CreatedAt`   | وقت إنشاء الحدث                       |
| `ProcessedAt` | وقت اكتمال المعالجة، أو `null` لو لسه |
| `RetryCount`  | عدد محاولات المعالجة                  |

مثال على رسالة محفوظة:

JSON

```
{
  "type": "TaskCompleted",
  "payload": {
    "taskId": "8f...",
    "employeeId": 12
  },
  "processedAt": null,
  "retryCount": 0
}
```

ده مثال توضيحي؛ شكل الـ JSON الفعلي هيعتمد على تصميمك.

### الخطوة الأولى: احفظ الـ Task والرسالة معًا

داخل Application Layer، بعد التحقق من صلاحية تغيير الحالة، تحدّث الـ Task وتضيف رسالة Outbox في نفس الـ transaction.

C#

```
await using var transaction =
    await dbContext.Database.BeginTransactionAsync(cancellationToken);

task.Complete();

dbContext.OutboxMessages.Add(new OutboxMessage
{
    Id = Guid.NewGuid(),
    Type = "TaskCompleted",
    Payload = JsonSerializer.Serialize(new
    {
        TaskId = task.Id
    }),
    CreatedAt = DateTime.UtcNow
});

await dbContext.SaveChangesAsync(cancellationToken);
await transaction.CommitAsync(cancellationToken);
```

الكود توضيحي، وافترضت إن `Task` و`OutboxMessages` بيستخدموا نفس `DbContext` ونفس قاعدة البيانات. في مشروعك، استخدم الـ abstractions الموجودة عندك بدل ما تخلي الـ Controller يتعامل مع `DbContext` مباشرة.

ليه الـ Transaction مهمة؟

* لو الحفظ فشل، مش هيتحفظ تغيير الـ Task ولا رسالة الـ Outbox.

* لو نجح، الاتنين هيتحفظوا معًا.

### الخطوة الثانية: خلّي Background Worker يعالج الرسائل

الـ Worker يقرأ الرسائل اللي `ProcessedAt` بتاعها `null`، وبعدها:

1. يقرأ الرسالة.

2. يستخرج `TaskId`.

3. يرسل الـ Notification.

4. يحدّث `ProcessedAt` بعد نجاح المعالجة.

لو الإرسال فشل، الرسالة تفضل غير معالجة، والـ Worker يحاول تاني وفق سياسة الـ Retry.

تقدر تستخدم Hangfire لتشغيل المعالجة دوريًا أو لجدولة عمليات المعالجة. لكن لازم تضمن إن الرسائل غير المعالجة هتتراجع تاني حتى لو التطبيق وقع أو الـ Job ما اتجدولش.

## 4. هل الـ Outbox Pattern يمنع التكرار تلقائيًا؟

لا، ودي نقطة مهمة جدًا.

افترض إن الـ Email اتبعت بنجاح، لكن التطبيق وقع قبل ما يحدّث `ProcessedAt`. لما الـ Worker يشتغل تاني، ممكن يبعت نفس الإيميل مرة ثانية.

عشان كده تحتاج كمان إلى Idempotency، مثل:

* `MessageId` ثابت لكل رسالة.

* تخزين الرسائل التي تمت معالجتها لمنع تكرار آثارها داخل النظام.

* استخدام Idempotency Key لدى خدمة الإرسال الخارجية، لو كانت تدعمه.

الـ Outbox يضمن إن الحدث ما يضيعش بسهولة؛ لكنه وحده لا يضمن إرسالًا خارجيًا مرة واحدة بالضبط.

## 5. هل تحتاجه في الـ Sprint الحالي؟

خلّي بالك من الفرق ده:

| المطلوب                                             | الحل المناسب                      |
| --------------------------------------------------- | --------------------------------- |
| محاكاة Notification باستخدام Logs                   | Hangfire Job + Structured Logging |
| إعادة محاولة المعالجة عند الفشل                     | Hangfire Retries                  |
| ضمان عدم ضياع الحدث بين حفظ الـ Task وجدولة الـ Job | Outbox Pattern                    |
| منع تكرار Notification حقيقية                       | Outbox مع Idempotency مناسبة      |

نصيحتي: لو متطلبات الـ Sprint عندك مجرد Task Completion Job وRetries وIdempotency، ومفيش طلب صريح لتنفيذ Outbox، ما تضيفش التعقيد ده من نفسك. افهم الفكرة ووضّح حدود الحل الحالي. أما لو مطلوب ضمان موثوقية الأحداث في الإنتاج، فالـ Outbox Pattern اختيار قوي.
